# 止损显示与查证记录

这项改动只增加显示和旁路观测，不改变止盈、止损、移动止损、强平、风控或对账的交易判断。

## 面板显示

移动止损状态来自执行器实际检查记录。K 线最高价、最低价、面板现价和管家快照不再用于确认“跟踪中”。
旧镜像没有观测能力、检查过期、标识不匹配、时钟异常或本轮没有实际检查时，显示未知。
新鲜检查确认未激活时，只说明本轮状态；重启前和缺口期间是否曾启动，仍保持未知。

执行器内部按实际费用后的净收益检查。面板展示其实际跟踪状态和净收益触发阈值；缺少同一次检查的费用与成交量口径时，
不把净收益阈值反算成精确价格，不画估算的移动价格线，也不按这个估算价格计算“锁定盈利”。
表格中的固定止损价格仍是账本计划价，其金额是按该计划价成交的预估净盈亏，不能保证成交价格或最终收益。

当前盘口参考显示买一、卖一、环境和获取时间，和执行器本次实际使用的价格分开展示。
平仓请求、方法返回、订单提交、原生成交回报是不同阶段；方法返回不代表订单成交。

## 两套独立证据

1. **执行器检查记录**：Docker 镜像补丁在原控制方法外增加观测包装，保留原返回、异常、比较符号和调用顺序。
   只记录原判断确实读取过的价格、净收益、阈值、跟踪状态、检查序号，以及原平仓/订单/成交回调阶段。
   没有被原判断读取的盘口一侧和标记价格保持空值，不能补成“执行器当时看到过”。
   原生记录位于 `vendor/hummingbot-api/bots/logs/stop_diagnostics/`，通过既有 bots 挂载持久化，
   独立有界写盘线程不依赖面板打开。日志保存有界，旧分段会轮转，需长期研究时应另行归档。
2. **独立公开行情记录**：主程序启动独立只读连接，仅订阅账本中未结束持仓的同环境 bookTicker 和 markPrice。
   不调用含同步和订单管理副作用的执行器 `positions()`，不接入策略、特征、管家或执行器。
   记录位于 `data/stop_quote_observations/quotes-*.jsonl`；`status.json` 给出当前进程 epoch、订阅、丢样和写盘错误。
   Demo 与主网不会相互回退。旧测试网没有这项旁路能力。

公开流保留交易所事件时间（缺失即空）、本地接收 UTC 时间、单进程单调时钟、连接 epoch 和本地序号。
断流、订阅变更、无有效消息、队列满和写盘错误均保留可识别的缺口信息。队列上限 2,048 条；公开流日志按 64 MiB 分段，
最多 16 段。记录缺失、进程重启、保留期外数据以及两次检查之间的行情，都不能被解释为“肯定没有漏触发”。

## 如何核对一次越线

先固定持仓、执行器标识、环境和时间段，再依次比对：

- 公开盘口旁路是否收到过相应买一或卖一价格，事件时间与接收时间是否有效，区间是否有断流/丢样。
- 执行器原检查实际使用的价格和净收益是否满足该次检查的原比较条件。成交 K 线越线不等同于盘口条件成立。
- 条件成立后是否进入平仓请求、实际订单提交；返回或异常是什么阶段。
- 原生成交回报、交易所挂单和交易流水是否证明部分或全部成交。没有回报不等于没有成交，也不等于已经成交。

旁路收到某个价格，只能证明旁路收到过，不能证明执行器同时收到过。
保命止损的触发还需要核对交易所实际订单的 workingType、触发价格和对应标记价。

## 更新与启用

普通程序更新即可去掉 K 线推算的错误显示，并启动独立公开盘口记录；旧执行器镜像的真实跟踪状态仍显示未知。
逐轮执行器检查和原生回调记录需要重建并启用包含本补丁的 Hummingbot 镜像。

**程序更新不会自动重启 Hummingbot。** 重启会丢失运行中的持仓执行器管理状态，必须先安排没有持仓、没有待成交执行器的维护窗口，
核对交易所、执行器和账本一致后再更新镜像。不要在有持仓时为了启用日志直接重启容器。
启用后应核对执行器原始 GET 回应中的 `position_executor_stop_v1` 能力、面板上新鲜的实际检查时间与递增序号，
并检查两套日志均有新记录。
本变更的离线回归不等于已经在运行中的账户启用了新镜像，也不构成触发或成交保证。
