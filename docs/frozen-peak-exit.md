# Frozen observed profit target

New Demo positions opt in by default through `fast_loop.frozen_peak_exit_on = true`. `fast_loop.frozen_peak_exit_after_s` defaults to 3600 seconds. The panel edits this duration in whole minutes (default 60, range 1–10080), converting to seconds for validated storage. Both settings appear under the position keeper in the settings panel and support hot reload. Set the freeze duration below that position’s maximum holding time; otherwise it will usually exit before the freeze. Changes apply only to positions created afterward; existing enrolled positions retain their persisted settings, and legacy positions without the state field are never enrolled. Live and legacy testnet execution do not create or evaluate this rule.

The timer starts at the first exchange fill of the identified entry order, obtained from its complete order-specific userTrades records. Sampling requires a fully filled terminal entry, complete actual USDT entry fees, matching remaining position direction and quantity, and a fresh same-environment execution book. The target uses the observed bid for longs and ask for shorts. Profit eligibility deducts actual entry commission plus an estimated exit taker commission using the configured taker fee captured at enrollment. Funding, slippage and future actual exit fees are not predicted, so the rule cannot guarantee a positive realized result.

The keeper samples at its normal review cadence. It stores only observed executable quotes consumed before the deadline, never candle extrema or mainnet feature prices. At the first review at or after the deadline, it freezes the best eligible earlier sampled price; that review cannot itself trigger a close or introduce a new peak. A subsequent fresh exchange quote must reach or pass that target in the profitable direction and still have positive estimated profit after both fees. No eligible positive sample by the deadline leaves this rule inactive for that position. Existing stop loss, take profit, keeper decisions and maximum holding time continue independently.

The registry atomically persists enrollment, verified fill times and costs, sample times, observed peak, frozen target, and evidence status. Once a retouch qualifies, its exit intent is latched before returning the keeper verdict. A restart or failed handoff retries that same intent through the existing idempotent close path even if the quote retreats or evidence becomes unavailable. Restarting retains the frozen target; missing observations are never reconstructed. Gaps are disclosed rather than described as a continuous market maximum. A changed entry basis permanently marks the rule unknown. Missing, stale, future, duplicate or out-of-order evidence cannot generate a close request. The keeper decision log includes `output.frozen_peak_exit`, including non-triggering evidence failures.

Read-only exchange evidence is fetched outside the symbol lock with a twelve-second total timeout. A read-only Demo timing sample took approximately 5.8 seconds for the complete evidence sequence; this single observation informed the budget and does not guarantee future latency or availability. The current registry identity, rule state, position status and protection evidence are checked again under the symbol lock before saving. A concurrent exit takes priority and cannot be overwritten by a late sample. On a qualifying retouch the keeper returns its normal close verdict, and the existing close path handles reduce-only execution, protection coordination and actual flat confirmation. The rule does not create a separate exchange take-profit order or claim a close is filled before verification.

`fast_loop.frozen_peak_evidence_mode` decides where that read sits. The default `sync` keeps it on the keeper review path: every review waits for it, and the routine review round waits for its slowest position before `keeper_interval_s` starts again. `background` moves it off that path: a one-second tick starts one read per open position every `frozen_peak_evidence_interval_s` (never two at once for the same position), and the result is cached with the time the read started. A review uses the cached result only while it is at most `frozen_peak_evidence_max_age_s` old (`0` = no age limit); a missing or older result skips the rule for that review, records `detail = evidence_stale` in `output.frozen_peak_exit`, and logs one warning per position until a fresh read arrives. A fresh triggering result produces the same close verdict as the synchronous path. In `background` mode the routine round also stops waiting for its reviews, so one slow position no longer delays the next round of the others; a position whose review is still running is skipped by the next round. All three settings hot-reload.

The read competes with the server-protection tick for the single client-side ccxt rate limiter (a leaky bucket of 20 weight per second, shared by every call of the exchange client). `positionSide/dual` costs 30 weight, so each call of it makes the next queued call wait 1.5 seconds, and the protection tick and the evidence read each make it several times per position. Calls queue in that bucket before any HTTP request is sent, so the ccxt request timeout does not bound the wait; the twelve-second total timeout above is what ends it.
